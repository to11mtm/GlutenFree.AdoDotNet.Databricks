# Thrift Transport Plan (future work — targeted for v0.3+)

Status: **Speculative / not started.** This document specs out what adding a
Thrift/HiveServer2 transport behind `IDatabricksTransport` would involve, so the
work can be picked up later without re-deriving the research.

## 1. Why a Thrift transport?

The current transport (`RestStatementTransport`) uses the public
[Statement Execution API](https://docs.databricks.com/api/workspace/statementexecution)
(`/api/2.0/sql/statements`). It is simple, documented, and stable — but it has
real limitations that a Thrift transport would lift:

| Concern | REST Statement Execution API | Thrift (HiveServer2/TCLIService) |
|---|---|---|
| Compute targets | SQL warehouses only | SQL warehouses **and** all-purpose/interactive clusters |
| Sessions | None (each statement is standalone) | Real sessions: `USE catalog/schema`, session confs, temp views persist |
| Latency | Submit + hybrid wait + polling; extra round trips per statement | Long-lived session; `ExecuteStatement` with DirectResults can return rows in one round trip |
| Result fetch | Chunked, external presigned links (Arrow) or inline JSON | `FetchResults` streaming, plus CloudFetch (presigned links) for large results |
| Row/size limits | 100 GiB / result, 25 MiB inline | Effectively the same backend limits, but no inline-JSON 25 MiB constraint |
| Protocol stability | Public, versioned, documented | De-facto stable (all official Databricks drivers use it) but **not a documented public API** |

Every official Databricks driver (JDBC, ODBC, `databricks-sql-python`,
`databricks-sql-go`, `databricks-sql-nodejs`) speaks Thrift, so the wire
behavior is well understood and battle-tested — those drivers are our primary
references for correct behavior.

## 2. Protocol overview

- **IDL:** Hive's `TCLIService.thrift` plus Databricks/Spark extensions
  (`TSparkGetDirectResults`, `TSparkArrowResultLink`, `TDBSqlSessionConf`, etc.).
  **Researched 2026-08: the extended IDL is not public.** Databricks maintains it
  in a private monorepo; every official driver repo (`-go`, `-python`, `-nodejs`)
  ships only generated code. (`databricks-sql-go` briefly carried the *stock Hive*
  IDL — no Spark extensions — and deleted it in 2022.) The most complete public
  representation is the **generated C# in
  [`apache/arrow-adbc`](https://github.com/apache/arrow-adbc)** under
  `csharp/src/Drivers/Apache/Thrift/Service/Rpc/Thrift/` (Apache-2.0, Thrift
  compiler 0.21.0, protocol enums through `SPARK_CLI_SERVICE_PROTOCOL_V9` /
  `HIVE_CLI_SERVICE_PROTOCOL_V11`, all extension structs present:
  `TSparkArrowResultLink`, `TSparkArrowBatch`, `TSparkParameter`,
  `TSparkGetDirectResults`, `TDBSqlSessionConf`, `canReadArrowResult` /
  `canDownloadResult` / `canDecompressLZ4Result` on `TExecuteStatementReq`).
  It was contributed/regenerated by Databricks employees, so it has de-facto
  official provenance. That C# is what we vendor — see §4.
- **Protocol version:** negotiate `SPARK_CLI_SERVICE_PROTOCOL_V6` (or newest
  the peer supports) in `OpenSession`. V5+ is required for Arrow + CloudFetch.
- **Transport:** Thrift-over-HTTP (`THttpTransport`), **not** raw sockets:
  - SQL warehouse endpoint: `https://<host>/sql/1.0/warehouses/<warehouse-id>`
  - All-purpose cluster endpoint: `https://<host>/sql/protocolv1/o/<org-id>/<cluster-id>`
  - Auth is the same `Authorization: Bearer <token>` header we already produce
    via `IDatabricksAuthenticator` (PAT and OAuth M2M both work unchanged).
  - Binary Thrift protocol (`TBinaryProtocol`) over the HTTP body.
- **Core RPC flow:**
  1. `OpenSession` → `TSessionHandle` (holds `sessionId` GUID bytes)
  2. `ExecuteStatement(sessionHandle, sql, confOverlay, getDirectResults, ...)`
     → `TOperationHandle`
  3. If DirectResults didn't complete inline: poll `GetOperationStatus`
  4. `GetResultSetMetadata` → schema (+ `arrowSchema` bytes when Arrow enabled)
  5. `FetchResults` loop → `TRowSet` containing either:
     - `arrowBatches` (inline Arrow IPC record batches, optionally LZ4-framed), or
     - `resultLinks` (`TSparkArrowResultLink[]` — CloudFetch presigned URLs), or
     - legacy `columns` (columnar Thrift values — we should *not* need this path)
  6. `CloseOperation`, and eventually `CloseSession`
- **Cancellation:** `CancelOperation(operationHandle)` — best effort, same
  semantics as our current REST cancel.
- **Parameters:** protocol V8+ supports native named parameters
  (`TSparkParameter`); earlier versions require client-side literal inlining.
  Our REST path already sends typed named parameters, so require a protocol
  version with parameter support and fail fast otherwise.

## 3. Fit against `IDatabricksTransport`

**Updated for the ADBC-wrapper decision (§4 Option D).** We map onto the public
ADBC surface (`DatabricksDriver.Open` → `DatabricksDatabase.Connect` →
`AdbcConnection.CreateStatement` → `AdbcStatement`), not raw Thrift RPCs.
Spike findings (verified by reflection against 0.23.0):

| Interface member | REST semantics today | ADBC mapping | Gap / decision needed |
|---|---|---|---|
| `ExecuteStatementAsync` | POST + hybrid wait + poll → `StatementResponse` w/ string `statementId` | `AdbcStatement.SqlQuery = sql; ExecuteQueryAsync()` → `QueryResult` (`RowCount` + `IArrowArrayStream`) | Transport synthesizes a `StatementResponse`: generates its own statement id, keeps a per-statement entry holding the live `AdbcStatement` + stream. Manifest schema must be built from the Arrow `Schema` — **watch item:** `ColumnInfo.TypeName`/precision/scale must be reconstructed from Arrow field types (+ any field metadata the driver carries); verify against live warehouse that this matches what `DatabricksTypeMap` expects. |
| `GetResultChunkAsync(id, chunkIndex)` | GET chunk N metadata/links | `IArrowArrayStream.ReadNextRecordBatchAsync()` — forward-only | Treat `chunkIndex` as "next expected", throw on out-of-order (reader walks forward only). Each batch is handed to the reader as an inline Arrow payload; avoid the base64 `Attachment` detour if possible (consider an internal seam so the reader can accept an in-memory `RecordBatch` directly without re-serializing). |
| `DownloadExternalLinkAsync` | GET presigned URL | Never called — CloudFetch is internal to the ADBC driver, which returns plain record batches | Implement as `NotSupportedException`; reader never sees external links from this transport. |
| `CancelStatementAsync` | POST cancel | `AdbcStatement.Cancel()` / `AdbcConnection.Cancel()` | None. |
| Sync counterparts | Genuinely sync via `HttpClient.Send` | `AdbcStatement.ExecuteQuery()` and `IArrowArrayStream` sync reads exist | Verify the ADBC "sync" paths aren't sync-over-async internally; if they are, document rather than fight it. |
| `IAsyncDisposable` | Disposes owned handler only | Dispose `AdbcStatement`s, `AdbcConnection` (closes Thrift session), `AdbcDatabase` | Straightforward ownership chain. |

Configuration mapping: our connection string → `DatabricksParameters` /
`SparkParameters` option dictionary passed to `DatabricksDriver.Open` /
`Connect` (host, http path, token/OAuth, catalog/schema, timeouts, CloudFetch
and LZ4 toggles). Enumerate exact option keys during implementation.

Additional connection-level items:

- **Session lifetime:** one `AdbcConnection` (= one Thrift session) per open
  `DatabricksConnection`. `Open` → `Connect`; `Close` → dispose. This finally
  gives `ChangeDatabase`/`ChangeCatalog` true session semantics (today we
  replay `USE` statements per command).
- **Session expiry/idle timeout:** surface ADBC/driver session-expired errors
  as a clear `DatabricksException` (broken-connection state), matching ADO.NET
  expectations. Do not auto-reopen silently.
- **Parameters:** `AdbcStatement` exposes Arrow-based `Bind`/`BindStream`;
  check whether the Databricks driver supports named parameters through ADBC
  options or binding — if not, fail fast (no client-side literal inlining).
- **Heartbeats:** not required; warehouses keep sessions alive while operations
  run. Document the idle timeout (~15 min typical) in the README.

## 4. Thrift codegen strategy

Since no public `.thrift` IDL exists (§2), "codegen" becomes "vendor the
arrow-adbc generated C#" (already generated with Thrift 0.21.0). We do HTTP
ourselves either way: serialize the request struct to a byte buffer, POST it
with our existing retry/auth/HTTPS-only machinery (sync **and** async),
deserialize the response buffer. This preserves the sync pipeline and keeps our
429/503/Retry-After handling in one place.

The remaining decision is how to satisfy the generated code's **Thrift runtime**
dependency (`TBinaryProtocol`, `TMemoryBufferTransport`, `TProtocol` entities,
`TApplicationException`, ...):

**Decision: Option D — wrap the ADBC Databricks driver (chosen 2026-08, supersedes Option C below).**
Ship the Thrift transport as its own NuGet package,
`GlutenFree.Databricks.AdoNet.Thrift`, implemented as a **wrapper around the
[`Apache.Arrow.Adbc.Drivers.Databricks`](https://www.nuget.org/packages/Apache.Arrow.Adbc.Drivers.Databricks)
NuGet** (0.23.0 at time of writing). Rationale:

- The package publicly exposes `DatabricksDriver` / `DatabricksDatabase` /
  `DatabricksParameters` — a complete Databricks-maintained Thrift client with
  sessions, DirectResults, CloudFetch, LZ4 and OAuth already implemented. Its
  generated Thrift types are `internal`, but we don't need them: the public
  ADBC API returns Arrow batches, which our reader already consumes.
- **Zero vendored/duplicated code**; protocol drift becomes an upstream
  package upgrade, not a re-vendoring exercise.
- Dependencies stay out of the base package: the add-on pulls
  `Apache.Arrow.Adbc.Drivers.Apache` (which brings `ApacheThrift` and its
  transitive AspNetCore/Extensions closure), `K4os.Compression.LZ4(.Streams)`,
  `Microsoft.IO.RecyclableMemoryStream`.
- Known caveats: ADBC packages are 0.x (public API may shift between
  versions — pin and upgrade deliberately); retry/session/timeout behavior is
  delegated to the ADBC driver rather than our REST-transport machinery; the
  "genuinely synchronous" guarantee depends on what the ADBC API offers
  (spike item). Transport mapping in §3 to be revisited against the ADBC
  surface (`AdbcConnection`/`AdbcStatement`) rather than raw Thrift RPCs.

Superseded options, kept for the record:

**Option C — separate add-on package with vendored generated structs.**
Ship the Thrift transport as its own NuGet package,
`GlutenFree.Databricks.AdoNet.Thrift`, which references the base provider plus
the `ApacheThrift` runtime NuGet. The base ADO.NET package keeps its minimal
dependency footprint; the 25 transitive packages only reach applications that
opt into the Thrift transport. This also avoids maintaining a vendored runtime:
we track ApacheThrift releases via normal package upgrades. The vendored
arrow-adbc generated structs live in the add-on package
(`src/GlutenFree.Databricks.AdoNet.Thrift/Generated/`). Wiring: the base
package's `Transport=Thrift` connection-string switch resolves the transport
factory from the add-on (exact registration mechanism decided in milestone 3 —
e.g. an explicit `Register()` call or a factory type on the connection).

Superseded analysis, kept for the record:

**Option A — reference the `ApacheThrift` NuGet (0.22.0) from the base package.**
- Measured (2026-08, `dotnet list package --include-transitive`, net8.0): pulls
  **25 transitive packages** into every consumer, including the Blazor stack
  (`Microsoft.AspNetCore.Components.Web`, `.Components`, `.Forms`,
  `Microsoft.JSInterop`, `Microsoft.AspNetCore.Authorization`),
  `Microsoft.Extensions.Logging.Console`/`.Debug` (+ Configuration/Options/DI
  chains), and `System.Net.Http.WinHttpHandler` — all to support server/Blazor
  transports we never touch. `Thrift.dll` itself is ~232 KB.
- Pros: zero maintenance, exactly what `apache/arrow-adbc` does
  (`<PackageReference Include="ApacheThrift" />`), easy upgrades.
- Cons: dependency pollution for an ADO.NET provider package; version conflicts
  with app-level `Microsoft.Extensions.*`/AspNetCore pins; poor trimming story.

**Option B — vendor the runtime subset we need.**
- Client-side binary-protocol-over-memory-buffer needs ~21 files, **~86 KB of
  Apache-2.0 source** out of `apache/thrift` `lib/netstd/Thrift/` (v0.21.0 to
  match the generated code): `Protocol/TBinaryProtocol|TProtocol|TBase|
  TProtocolException|TProtocolFactory|ToString`, `Protocol/Entities/*` (8 files),
  `Protocol/Utilities/TProtocolUtil|TGuidExtensions`, `Transport/TTransport|
  TEndpointTransport|TTransportException`, `Transport/Client/
  TMemoryBufferTransport`, `Collections/TCollections`, `TApplicationException`,
  `TBaseClient`, `TConfiguration`, `TException`. Skipped entirely: compact/JSON
  protocols, all socket/pipe/HTTP transports, server, processor.
- Pros: **zero new NuGet dependencies**; trims cleanly; runtime pinned to the
  same version the code was generated with; we already own the HTTP layer.
- Cons: ~86 KB of vendored code to maintain; manual (rare) upgrades — but the
  binary protocol wire format has been stable for a decade.

Vendored-code provenance rules (both the generated structs and any runtime
files): keep upstream license headers, record source repo + commit hash + a
refresh script under `Transport/Thrift/`, mark everything `internal`, exclude
from coverage, suppress style analyzers for the folder via `.editorconfig`.

Note: arrow-adbc's generated code is `internal` in their tree; vendoring
requires re-namespacing (e.g. `GlutenFree.Databricks.AdoNet.Transport.Thrift.Generated`)
which the refresh script should do mechanically.

## 5. Result decoding

Good news: the hard part is already done. `ArrowResultDecoder` /
`DatabricksTypeMap.ConvertArrowValue` consume Arrow IPC record batches and are
transport-agnostic. Thrift work is only about *acquiring* the bytes:

- `arrowBatches`: each `TSparkArrowBatch.batch` is an IPC record batch **without
  the schema preamble** — prepend `GetResultSetMetadata().arrowSchema` to form a
  valid IPC stream before handing to `ArrowStreamReader`. Handle optional
  LZ4-frame compression (`lz4Compressed` flag) — we already reference
  `Apache.Arrow.Compression`.
- `resultLinks` (CloudFetch): identical to today's EXTERNAL_LINKS path;
  links expire (~15 min), so keep the existing just-in-time download model.
  Set `canDownloadResult=true` in `ExecuteStatement` to opt in.
- Set `canReadArrowResult=true` and request `TSparkArrowTypes` with
  `timestampAsArrow`, `decimalAsArrow`, `complexTypesAsArrow`,
  `intervalTypesAsArrow` = true so decoding matches the REST Arrow shapes we
  already test (complex types as genuine nested arrays, intervals as Arrow
  interval arrays).
- **Watch item:** verify TIMESTAMP_NTZ and interval representations match
  the REST-Arrow behavior our reader expects; add integration tests that run
  the full extended-types matrix through the Thrift transport.

## 6. Configuration surface

Connection-string additions (builder + docs):

- `Transport=Rest|Thrift` (default `Rest`) — selects the transport factory.
- `HttpPath=/sql/1.0/warehouses/<id>` — optional explicit path; defaults to the
  warehouse path derived from `WarehouseId`; required form for all-purpose
  clusters. (JDBC/ODBC users will recognize `HTTPPath`.)
- Existing settings reused as-is: `Host`, `Token`/OAuth settings,
  `CommandTimeout`, `ConnectionTimeout`, catalog/schema.

`DatabricksConnection` gains a small transport-factory switch (the
`TransportFactory` test hook already exists). Shared `HttpClient` from
`DatabricksSharedResources` is reused for both Thrift POSTs and CloudFetch
downloads.

## 7. Testing plan

- **Unit:** fake Thrift server = in-memory handler that speaks
  binary-protocol-over-HTTP (serialize expected responses with the same
  generated code); cover OpenSession negotiation, DirectResults short-circuit,
  poll loop, arrowBatches schema-prepend, LZ4 batches, CloudFetch links,
  forward-only chunk guard, cancel, session close on dispose, sync parity.
- **Integration:** run the *entire existing* integration suite (all 5 fixtures)
  a second time with `Transport=Thrift` via a test-collection parameter or env
  var (`DATABRICKS_TRANSPORT=thrift`) — the fixed versioned-schema/run_id
  pattern needs no changes. Add a session-semantics test (`USE schema` sticks
  across commands) that only runs on Thrift.
- **Dialect/linq2db:** no changes expected — SQL generation is
  transport-independent — but run the linq2db integration fixtures on Thrift
  once as a smoke pass.

## 8. Risks & open questions

1. **Unofficial protocol:** TCLIService + Spark extensions are not a documented
   public API. Mitigation: pin behavior to what `databricks-sql-go`/`-python`
   do; keep REST as the default transport.
2. **IDL drift:** the extended IDL is private and still evolving (the Go driver
   recently reverted a new field, `enforceEmbeddedSchemaCorrectness`). Vendor
   the arrow-adbc generated C# with source repo + commit hash + refresh script;
   refreshes are deliberate, not automatic. No public source currently exposes
   anything past `SPARK_CLI_SERVICE_PROTOCOL_V9`.
3. **Thrift runtime dependency:** verified 2026-08 — ApacheThrift 0.22.0
   supports net8.0 but drags 25 transitive packages (see §4). Decision:
   Option A (NuGet) vs Option B (vendor ~86 KB runtime subset, preferred).
4. **Parameter support:** confirm minimum protocol version for
   `TSparkParameter` named parameters on both warehouses and all-purpose
   clusters; decide whether pre-V8 peers get an error or literal inlining
   (error preferred — inlining reintroduces injection risk).
5. **GetSchema:** Thrift offers metadata RPCs (`GetCatalogs`, `GetSchemas`,
   `GetTables`, `GetColumns`) — optional optimization; the existing
   `information_schema` queries work unchanged, so defer.
6. **Cloud Fetch link expiry under slow consumers:** links live ~15 min;
   confirm re-fetch behavior (`FetchResults` with same start row?) or document
   the limitation, mirroring what the Go driver does.

## 9. Suggested milestones

Status 2026-08: 1–3 implemented (ADBC-wrapper form); 4 partially — unit tests
done, dual-transport integration run pending a live warehouse.

1. **Spike (done):** verified ADBC public API fit by reflection; no vendored code needed.
2. **Transport (done):** `ThriftStatementTransport : IDatabricksTransport` in the
   `GlutenFree.Databricks.AdoNet.Thrift` add-on package — session per transport,
   `USE CATALOG`/`USE SCHEMA` replay on change, per-statement query timeout,
   cancel, sync parity via ADBC sync API, results delivered as a live
   `IArrowArrayStream` through the new `ResultData.ArrowStream` seam (reader
   drains and disposes it; statement released on stream dispose). ADBC driver
   errors are translated to `DatabricksException`. **Named parameters** are
   emulated with `EXECUTE IMMEDIATE '<sql>' USING CAST('<value>' AS <type>) AS name`:
   the server resolves the `:name` markers natively (no client-side SQL
   parsing), values appear only inside strictly-escaped string literals, and
   names/type-names are validated against strict shapes — this sits below the
   ADO.NET surface, so Dapper and linq2db work unchanged (verified live).
3. **Wiring (done, first form):** `connection.UseThriftTransport()` extension
   (pre-open); connection-string `Transport=Thrift` switch deferred — the base
   package cannot reference the add-on, so a string-keyed switch needs a
   registration mechanism (future).
4. **Test matrix (done):** reader `ArrowStream` unit tests; EXECUTE IMMEDIATE
   escaping/injection unit tests (`GlutenFree.Databricks.AdoNet.Thrift.Tests`);
   dual-transport integration runs via `DATABRICKS_TRANSPORT=thrift` (verified
   live 2026-08: 22/22 core integration and 27/27 linq2db integration pass on
   both transports — including the full numeric/extended type matrix, so
   Arrow→Databricks type-name reconstruction is confirmed against
   `DatabricksTypeMap`); Thrift-only session-semantics tests (catalog/schema
   persist across commands; `ChangeDatabase` switches the live session).
5. **Stretch:** all-purpose cluster support, native named parameters, Thrift
   metadata RPCs for `GetSchema`, session-conf passthrough.
